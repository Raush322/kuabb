# Архитектура Learning Intelligence + Banking

## Цель системы

Learning Intelligence + Banking — закрытый онлайн-журнал и intelligence dashboard для корпоративного обучения. Система собирает материалы из заранее настроенных внешних источников, выявляет значимые сигналы и объясняет, как они могут повлиять на развитие сотрудников, learning-функцию, навыки, технологии и бизнес.

Главный результат для пользователя — не просто список новостей, а ответ на три вопроса: что изменилось, что это меняет в работе или навыках и почему это может быть важно для корпоративного обучения.

## Основные компоненты

| Компонент | Назначение | Этап |
|---|---|---|
| Web-приложение | Закрытый журнал, поиск и фильтры, страницы статей, административная панель. | MVP |
| PostgreSQL | Источник истины: статьи, настройки, результаты анализа, роли и редакторские решения. | MVP |
| RSS-коннектор | Получает материалы из RSS-лент и приводит их к единому виду. | MVP, первый сценарий |
| Планировщик задач в приложении | По расписанию запускает ограниченный RSS-сбор на первом этапе. | MVP, временная реализация |
| AI-анализатор | Классифицирует материалы и формирует структурированный редакторский вывод. | MVP |
| Контракты коннекторов | Единый интерфейс для RSS, API, Sitemap и Web. | MVP: контракт; позднее: реализации кроме RSS |
| Очередь и отдельный worker | Надёжно и независимо выполняют сбор, извлечение текста и AI-анализ. | После первого вертикального сценария |
| Redis | Хранит очередь задач и краткоживущие технические состояния. | После первого вертикального сценария |
| Docker Compose | Единый локальный и серверный запуск нескольких компонентов. | После первого вертикального сценария |

Роли пользователей: `ADMIN` управляет пользователями и всеми настройками; `EDITOR` модерирует материалы, редактирует классификацию, digest и редакционные настройки в пределах выданных прав; `VIEWER` читает опубликованный журнал и может оставлять feedback.

## Поток данных

```text
ADMIN / EDITOR настраивает источник и RSS-feed
  → планировщик создаёт collection_run
  → RSS-коннектор получает записи
  → нормализация URL, метаданных и текста
  → проверка дубликатов по canonical_url и content_hash
  → сохранение статьи и технического результата collection_item
  → правила исключения и первичный отбор
  → AI-анализ структурированного результата
  → темы, теги, тип контента, релевантность и объяснение
  → редакторская модерация
  → опубликованный материал видит VIEWER
  → feedback сохраняется для последующего улучшения правил и промптов
```

Сбор и анализ фиксируются отдельно: `collection_runs` и `collection_items` отвечают на вопрос «что технически произошло», а `article_analysis` — «какой редакционный вывод был сделан».

## Границы web-приложения и worker

На раннем MVP web-приложение содержит интерфейс, API, запуск RSS-сбора и обработку небольшой очереди задач. Это намеренное упрощение для локального запуска на Windows.

Граница уже должна быть выражена в структуре модулей: web-приложение не знает деталей RSS-парсинга и AI-вызовов, а вызывает прикладные сервисы через ясные команды: «запустить сбор», «обработать материал», «повторить анализ». Поэтому позднее эти же сервисы можно перенести в отдельный worker без изменения интерфейса или схемы БД.

После появления нескольких источников и регулярных запусков worker будет забирать задачи из очереди Redis. Web-приложение будет только создавать задачи и показывать их состояние. Redis не является хранилищем бизнес-данных: итоговые данные и аудит всегда остаются в PostgreSQL.

## PostgreSQL, Redis и AI

**PostgreSQL** хранит все постоянные данные, включая настройки источников и правил, связи статей с темами/тегами, решения редактора, результаты запусков и версии AI-промптов. Регулярные логические резервные копии и проверка восстановления обязательны до серверного запуска.

**Redis** предусмотрен исключительно для очередей и повторов задач. Он появится вместе с отдельным worker, а не до необходимости параллельной или длительной обработки.

**AI** получает только нужный для анализа контекст: очищенный текст или его разрешённый фрагмент, метаданные статьи, активные редакционные правила, темы, теги и версию промпта. Результат обязан соответствовать JSON-схеме: релевантность, оценка, обоснование, summary, business context, learning implications, key signals, темы, теги и content type. Приложение валидирует ответ до сохранения.

Внешняя статья является недоверенными данными: её текст не может отменять системные инструкции. Для аудита сохраняются модель, версия промпта, время анализа и статус ошибки. Политика провайдера AI и требования банка к передаче внешних данных должны быть согласованы до production.

## Хранение внешнего контента

Полный текст внешнего материала не является обязательным бессрочным полем БД. Используется управляемая политика хранения:

1. При сборе извлекается очищенный текст и создаётся `content_hash`.
2. Для AI передаётся текст либо разрешённый фрагмент в пределах установленных лимитов.
3. По умолчанию в PostgreSQL хранятся метаданные, выдержка, хеш, ссылка на источник и структурированный результат анализа, а не полный текст.
4. Если источник и правовые условия разрешают временное хранение, очищенный текст помещается в отдельное техническое хранилище с `retention_until` и автоматически удаляется по политике хранения. Эта возможность проектируется, но не требуется для первого MVP.
5. Повторный анализ использует сохранённый разрешённый фрагмент, если он ещё не истёк; иначе материал повторно извлекается по URL при условии, что источник доступен и это разрешено его правилами. Если это невозможно, редактор видит, что повторный анализ недоступен без нового получения источника.

Такая политика снижает риск бессрочного копирования внешнего контента, но означает, что URL может исчезнуть или измениться. Неизменным доказательством обработки остаются метаданные, хеш, дата, версия промпта и редакторское решение.

## Расширение системы

Новые способы получения данных добавляются как коннекторы общего контракта: `RSS`, `API`, `SITEMAP`, `WEB`. Типы уже есть в данных и административном интерфейсе. В первом вертикальном сценарии реализуется только `RSS`; остальные типы нельзя включать до появления и тестирования соответствующего коннектора.

Возможные будущие расширения: отдельный worker и Redis, API/Sitemap/Web-коннекторы, серверное развёртывание, автоматизация digest, уведомления и интеграции. Они не меняют основную модель «источник → материал → анализ → редакторское решение → журнал».

## Границы MVP

В MVP входят: закрытый журнал, роли `ADMIN`/`EDITOR`/`VIEWER`, PostgreSQL, управление источниками/фидами/темами/тегами/правилами/промптами, RSS-сбор, дедупликация, AI-анализ, ручная модерация, feedback, журналы запусков и ручной digest.

Отложены: отдельный worker, Redis, Docker Compose, реализации API/Sitemap/Web, trends, notifications, Telegram, bookmarks, comments, recommendation engine, vector database, semantic search, сложная аналитика и автоматические рассылки.
